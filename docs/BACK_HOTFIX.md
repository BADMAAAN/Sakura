# SAKURA 0.2.1-back — кандидат hotfix

Дата: 16 октября 2026, Europe/Moscow. Основа: `548cb046` / установленная SAKURA 0.2.0. **Физический PASS пользователя:** BLE Spam → режим/параметры → вращение → короткий Back → новый вход энкодером. Эта проверка не запускала Start и не подтверждает отмену всех унаследованных активных BLE-инструментов. После неё начата инвентаризация следующего пакета функций.

## Причина и воспроизведение

GPIO в исходниках соответствуют T-Embed CC1101 Plus: верхняя Back — GPIO6, нажатие энкодера Select — GPIO0. Перепутанные GPIO не подтверждены. Найдены несколько независимых программных причин:

- `ble_info` ждал исключительно Select и игнорировал Back.
- Пять локальных BLE-циклов стирали Back при наличии вращения Prev. Обход для плат с общей кнопкой Prev/Back ошибочно применялся к энкодерной плате.
- Whitelist, Media и Ninebot повторяли меню после уже потреблённого Back.
- Сканирование ожидало блокирующий `getResults(duration)`, поэтому UI не обрабатывал отмену до его завершения.
- Уровневый ввод повторял удерживаемые кнопки; input task стирал непотреблённые флаги через 75 ms. Это могло потерять короткий Back или перенести удержание на следующий экран.

До правки диагност воспроизвёл четыре дефекта ограниченным host-fixture. Тестер независимо получил четыре поведенческих FAIL в пяти проверках реальных извлечённых обработчиков. Сценарий ложного Start требует одновременно Back, Prev и ожидающего Select; одиночный Back → Start не доказан. Исходный reproducer сохранён с checkpoint.

## Контракт и реализация

Энкодер выбирает текущий пункт. Back имеет приоритет над ожидающими Select/вращением; короткое нажатие возвращает на предыдущий уровень. Home потребляет Back без выбора пункта. Одна устойчивая фронтовая пара press/release даёт одно действие; debounce — 20 ms стабильного состояния, удержание не повторяет действие. Жесты Deep Sleep/Restart и оформление сохранены. Wake-input поглощается до отпускания.

На этом SAKURA-target input task сохраняет события до потребления. Ожидание `AnyKeyPress` тоже потребляет соответствующие кнопочные флаги, чтобы сообщение не закрывалось вместе с последующим экраном одним нажатием.

Сканирование использует API установленной NimBLE-Arduino 2.5.1: неблокирующие `start`, `isScanning`, `getResults()` и проверяемый `stop`. Back проверяется до запуска, в ожидании и на границе завершения. UI показывает `Cancelling...` до запроса stop. Результаты очищаются только после фактического завершения. Чужое уже работающее сканирование не останавливается. При ошибке stop экран сохраняет владение операцией; следующий Back повторяет stop, возврат происходит после реального прекращения scan. Создания/принудительного удаления задач нет. События ожидания не переходят в результаты или родительское меню.

Подробный trace по умолчанию выключен (`SAKURA_INPUT_TRACE=0`). Опциональный `-DSAKURA_INPUT_TRACE=1` включает кольцо на 16 записей: время, физический источник, тип, постоянный screen ID, действие и результат. Вывод кольца производится при выходе из Buttons, не из input task. Имена устройств, адреса, пароли и содержимое пользовательских полей не записываются.

Settings → Diagnostics → Buttons показывает источник, последнее логическое событие, короткое/долгое нажатие и release/вращение, счётчик и время распознавания. Сбор наблюдений включён только на этом экране. Back немедленно закрывает его. Значение recognition для длинного удержания включает порог long, а не обозначает задержку короткого нажатия.

Свежая исходная база: **72 host-теста PASS**, это новый запуск, а не число из старого отчёта. Итог: **89 host-тестов PASS**, включая 17 новых Back-проверок; последний полный запуск — 29.144 s. Последняя сборка `flux-delta` PASS (142.61 s после первоначальной полной 445.59 s). Приложение 4 397 360 B (+3 040 B); статическая RAM 133 232 B (+72 B), свободно в app-разделе 255 696 B. SHA-256 application-only: `4ea389a184c3b327308716b7b87dbbb845e419b86c6e2f610ad07376f2a5a185`. Независимая проверка ESP32-S3 chip9, checksum и validation hash PASS; все изменённые объекты новее исходников. Параметры конкретного образа находятся в `artifacts/sakura-back-validation.json` и актуальном PROJECT_STATUS.

Реальные native-вызовы команды: `spawn_agent(back_diagnosis, debugger)` — GPIO/цепочка ввода и baseline repro; `spawn_agent(back_tests, tester)` и `followup_task` — RED→GREEN и fake scan; `spawn_agent(ble_hotfix, implementer)` — BLE-правки; `spawn_agent(hotfix_review, code_reviewer)` — независимые Home/FastPair/callback findings и перепроверка; `spawn_agent(hotfix_build_audit, build-engineer)` — образ/размер/разметка. Root интегрировал ввод и Diagnostics, исправил замечания и единолично работал с COM. Источник доказательств вызовов — native history; компактные результаты сохранены локально в `.codex/agent-team`.

Новые проверки выполняют реальный `InputHandler`, общий `check`, `loopOptions`, BLE list/config/prompts/info, scan helper, wrapper FastPair и модуль Diagnostics с безопасными заглушками. Покрыты Back до старта/при ожидании/scan/на результатах/в конфигурации, совместное завершение, ошибка stop, занятый чужой scanner, удержание/release/bounce, быстрый Select→Back, повторные Back, wake, отсутствие ложного Start/повторного входа, Home Back→новый Select и 100 циклов start/cancel. Число fake-сессий не является измерением задач FreeRTOS или heap устройства.

Аналогичные пути: общий menu handler используется Settings/Wi-Fi/QR; Files получил такое же ограничение обхода Prev/Back только платами HAS_3_BUTTONS. Имеющиеся QR/storage/sleep/render tests сохраняются. Полной аппаратной проверки этих разделов нет.

**Открытые ограничения P0:** синхронные connect/discovery и длинные рабочие циклы BLE Suite/Ninebot ещё могут задерживать Back; общие HID cleanup вызывают унаследованный глобальный deinit и не квалифицированы для параллельного владения Bluetooth. Подключение Wi-Fi также имеет унаследованное блокирующее ожидание. Эти пути не запускались и не объявляются исправленными. Активные передачи, команды, эксплуатация устройств и радио-спам в проверках не выполнялись.

Исторические 1.996231 s — время от последнего encoder sample до следующего DELTA present без идентификации события/экрана/wake. В прежней записи не было timestamp Back/Select. Причину конкретного выброса восстановить нельзя; длительность scan не выдаётся за задержку кнопки. Новые host debounce/stop интервалы не являются замером физической реакции LCD. Аппаратные input-to-visible, stop latency, task counts и долговременный heap ещё не квалифицированы.

## Сохранение и следующий шаг

Приватный checkpoint: `C:\Projects\FLUX-Backups\sakura-back-hotfix-20261016`. Содержит source ZIP и полный прежний комплект с зависимостями, application-only 0.2.0, ELF, build settings, SHA-256, свежий полный дамп 16 MB и проверку соответствия. Прочитанное приложение побайтно совпало с сохранённым 0.2.0: `0c7f13cbce29f5a2adf13328ace7cd783e417467e526a7aa8d90e06a6b51b0f3`. HEAD отличается от firmware revision `375015cd` только документацией. Дамп не входит в публикуемые файлы.

Устройство проверено как ESP32-S3/16 MB; текущая таблица совпадает с checkpoint: app `0x10000`, размер `0x470000`, данные с `0x480000`. Установка допускает только app-only в проверенный существующий раздел с verify и сравнением защищённых областей. Erase, форматирование и изменение NVS/разметки не применяются.

**Установка кандидата PASS:** записано только приложение по `0x10000`. Отдельный verify подтвердил три совпадения digest: приложение, весь префикс `0–0x10000` и данные `0x480000–0x1000000`. Сравнение выполнено до reboot с самым свежим `immediately-before-hotfix-flash-16MB.bin` (SHA-256 `f4a955e143ab9eb4ffa57a4cfcd490fc3d7eebc553ac89c67465189ebecbfc31`). За 20 секунд после загрузки panic 0; четыре окна Home renderer 62.31–62.35 FPS, render 5.538–5.552 ms, transfer 5.228–5.299 ms. Это cadence renderer, а не частота физического LCD или замер задержки Back.

Heap snapshot прежней 0.2.0 перед обновлением: free 144 967 B / total 267 651 B; после загрузки кандидата: free 145 459 B / total 268 091 B. Free PSRAM в обоих случаях 8 043 660 B. Снимки сделаны в разные моменты; улучшение памяти, минимум heap и отсутствие утечек по ним не заявляются. Физические многократные open/close и task/callback counts ещё не измерены.

Пользователь выполнил безопасный сценарий Bluetooth → BLE Spam → выбор режима/параметров без Start → вращение → короткий Back и новый вход. Ответ: «Да, Back возвращает и повторный вход работает».
